# HakurouPaper 设计原则

本文是产品与技术决策的上层约束。除非用户明确决定改变产品方向，否则功能、交互、视觉与技术选型都应服从这些原则。

## 1. 产品定位

HakurouPaper 是一款本地优先、低门槛、面向长文档与论文写作的 Markdown 编辑器。用户不应被 Markdown 语法、云服务账号或复杂配置阻挡；文件本身必须始终保持可迁移、可读和可被其他工具继续使用。

## 2. 本地优先与开放文件

- 文稿以标准 Markdown 保存，图片等资源使用相对路径。
- 不属于 Markdown 的展示设置（例如表格三线表、对齐和缩进）保存于同级资源目录的 `hakurou.json`；不得把自创标记写回 Markdown 正文。
- 文档级展示设置优先于软件级默认值；软件级默认值只保存在本机，不应覆盖已有的文档级选择。首行默认缩进只作用于正文段落，不能误作用于标题、图片或公式块。
- 不把用户内容锁进私有数据库或专有格式。
- 未保存只提示，不自动保存、更不自动提交 Git。
- 打开、保存、导出与分享必须由用户显式发起。
- 菜单的悬停二级层级应容错：短暂停留后再展开；一旦展开，除非用户点击外部或执行菜单操作，不因短暂移开鼠标而消失。

## 3. 轻量、稳定优先于功能堆叠

- 架构固定为 Tauri（Rust 后端 + Web 前端），避免引入重量级桌面壳。
- 每项新能力必须先保证输入、光标、保存、切换文稿等基本写作路径不受影响。
- 不为“看似完整”的功能引入整套与现有界面冲突的框架 UI。
- 性能、可输入性和文稿内容安全的优先级高于炫技效果。

## 4. 所见即所得，但 Markdown 是事实来源

- 编辑时尽量以自然排版呈现标题、列表、公式、图片等内容。
- 生成和保存的内容仍应是规范 Markdown；必要时允许用户查看、编辑其源码。非 Markdown 展示信息仅可作为可删除、可重建的外置元数据存在，不能影响其他工具读取正文。
- 对公式、引用等结构化内容，必须同时具备“渲染态”和“回到源码修改”的可靠路径。

## 5. 极简且克制的界面

- 默认界面服务写作，不占用中央编辑空间。
- 使用细线、留白、颜色和排版表达层级；避免不必要的圆角卡片、阴影和装饰性控件。
- 代码块等语义明确的内容可使用低对比度深底色与等宽字体区分正文，但不使用厚重边框或高饱和色块。
- 顶部为应用菜单与窗口控制，左侧为可扩展的工作区入口，底部状态栏保持简洁稳定。
- 界面文案支持中文与 English 切换；语言偏好只影响本机界面，绝不翻译、改写或污染用户文稿。
- 字体属于文稿阅读/编辑体验而非系统界面字体。预设要少且语义明确；自定义字体只引用用户本机已安装的字体名称，不打包、上传或复制字体文件。字体粗细只作用于正文，标题保持自己的排版层级。
- 功能可以隐藏或按需出现，但不能依赖用户记住 Markdown 语法。
- 对空行插入、表格等结构化写作能力，优先以鼠标可发现的按需入口提供，并写回标准 Markdown；不要为低频操作常驻工具栏。
- 空白行“+”入口可复用基础块转换能力，并按“正文/标题、列表/代码、表格/分隔线”分组；同类低频操作要保持紧凑一致，不重复制造彼此矛盾的菜单。
- 文稿末尾必须保留自然的继续写作路径：用户点击最后一个内容块之后即可落笔，但空白落笔区不能因重复点击无限制造空段落。
- 图片、表格等非文本对象应提供与文字菜单区分的轻量对象菜单；无语义持久化的视觉开关必须明确其边界，不能伪装成已写入 Markdown 的格式能力。
- 所有悬浮菜单都必须感知当前窗口边界，靠近边缘时自动调整位置，不能被裁切；一旦用户已经主动打开菜单，只能由点击外部或完成操作关闭，不能因鼠标短暂移开而消失。
- 悬浮入口必须允许鼠标从正文跨越到控制柄：不能因一次正常的指针移动立刻消失；短暂缓冲仅用于可点击性，不得妨碍用户切换到另一种对象菜单。
- 同类控制柄的位置必须一致：文字、图片、表格都从内容左侧出现；菜单以控制柄为锚点向外展开，空间不足时再反向或夹紧，不能因对象类型改变基本方向。
- 二级悬浮菜单应延迟展开、显式收起，并在新的主入口打开时重置暂存的预览状态；不能把上一次悬停的表格尺寸等临时状态泄漏到下一次操作。
- 对同一视觉语义的开关，应复用已经验证的视觉值并在关闭时显式恢复基线；不能依赖清空 class 或浏览器默认样式来“猜测”恢复结果。

## 6. 符合桌面软件习惯

- 支持新建、打开、保存、撤销/重做、标签页、未保存标识与关闭前确认。
- 多文稿切换必须保留各自内容、光标体验和未保存状态；不得闪烁或重置内容。
- 窗口拖动、最小化、最大化、关闭等基础系统操作属于发布前阻断项。

## 7. 学术工作流面向长期演进

- Pandoc 与指定 `.docx` 模板导出是核心交付能力。
- 文献能力以本地 Zotero/BibTeX 为基础，引用语法和文稿可在其他 Markdown 工具中使用。
- GitHub/Gitee 集成服务于身份、版本与同步；先提供明确可控的手动操作，再讨论自动化。

## 8. 先验证，再交付

- “能构建”不等于“功能可用”。
- 涉及输入、焦点、窗口、文件、公式、图片、导出、Git 的改动，必须进行与风险匹配的真实交互验证。
- 若验证不充分或发现问题，必须明确标为“试验中/未验收”，不得表述为“已支持”。

## 9. 修复要收敛，不积累补丁层

- 修复必须先定位到数据流、生命周期或边界上的根因；不能只叠加显示条件、延时或额外状态来掩盖现象。
- `App` 只负责工作区状态和功能编排；编辑器、公式、图片等能力按边界放入独立模块，避免一个功能侵入全部代码。
- 试验路径失败后应删除或回退其残留实现，不保留长期不可达的兼容分支。
- 不再维护独立“公式实验台”等与正文写作路径重复的实验工作区；公式能力只应服务于文稿内的标准 LaTeX Markdown。
- 新依赖、全局监听器和常驻状态必须说明必要性；如果一个小功能需要扩大基础架构，先做隔离原型并评估替代方案。

## 10. 品牌与版本纪律

- 正式产品名固定为 `HakurouPaper`；所有用户可见文字、文档、应用标题、安装包与图标应保持一致。
- 版本号仅用于功能发布或修复发布，不得因图标、文案或其他视觉微调单独递增。
- 品牌图标采用深黑墨绿底与粉色钢笔花瓣；在小尺寸下优先保证轮廓识别度，避免与整体扁平、克制的界面语言冲突。

## 11. 环境可追溯

- 项目使用的目录、运行入口、构建产物、文档和资源位置必须集中记录在《环境与位置说明》中。
- 路径或开发流程发生变化时，同步更新该说明，避免协作中依赖口头记忆寻找环境。
